📖 SmartEmbedAgent — Methodology

How the recommendation is actually computed

← Back to recommender GitHub ↗
TL;DR

We profile your corpus (PII, language, token distribution), profile your machine (RAM, CPU/MPS/GPU), score a fixed pool of open-source embedding models against the resulting constraints, and surface the top 3 with concrete operational numbers (index size, throughput, suggested reranker, prompt prefixes). When you tick Use local LLM agent, a local Ollama model overlays its own judgment on the model-pick / rationale / chunking / fine-tuning fields; the deterministic numbers stay the same.

1. Overview — the pipeline

Every recommendation goes through a fixed five-step pipeline. Steps 1–3 are deterministic Python; steps 4–5 are math+lookup; step 6 (optional) is the local LLM agent overlay.

  1. 1
    Profile the machine. Read RAM via psutil, detect CUDA / ROCm / Apple Silicon MPS via torch, surface unified-memory size on M-series Macs.
  2. 2
    Sanitize the corpus. Run regex + Hugging Face NER + opt-in regional packs (India: Aadhaar with Verhoeff validation, PAN, Indian mobile, vehicle registration) to redact PII before any analysis. Optional Microsoft Presidio backend for 50+ entity types.
  3. 3
    Analyze the cleaned corpus. Tokenize, compute p50 / p95 / p99 token-length distributions, detect language(s) via langdetect + script heuristics, calculate type-token ratio + domain-indicator terms.
  4. 4
    Filter the candidate pool. Drop models that don't fit the hardware (no GPU + needs-GPU-for-speed). Drop English-only models when the language profile is multilingual.
  5. 5
    Score & rank. Primary: context window matches the corpus's p95. Secondary: task-aware preference bumps. Tertiary: distance from target window. Take top 3.
  6. 6
    Compute deterministic add-ons. Index size (dim × doc_count × 4 bytes), embed throughput (CPU vs MPS rates per model), reranker recommendation (English vs multilingual), per-model prompt-prefix templates.
Optional step 7 (LLM agent overlay): if you set use_llm=true, the LangChain agent loop runs the same tools above and synthesizes its own judgment fields (model pick, rationale, chunking_strategy, fine_tuning_advice, hardware_fit_analysis). We merge these on top of the deterministic baseline — so the index/throughput/reranker/language fields are always present and consistent regardless of whether the LLM was used.

3. Hardware profile

Detection runs in this order; first match wins:

  1. NVIDIA / CUDA — torch.cuda.is_available() + torch.cuda.get_device_properties(0).total_memory
  2. AMD / ROCm — torch.version.hip set, then re-uses the CUDA-shaped API surface that PyTorch exposes against ROCm
  3. Apple Silicon / MPS — checks torch.backends.mps.is_available() on Darwin/arm64, parses chip name from sysctl -n machdep.cpu.brand_string, surfaces unified-memory size (= total RAM)
  4. CPU fallback — populated whenever none of the above succeed

For Apple Silicon, gpu_memory_gb is reported as 0.0 (the convention is discrete VRAM); use unified_memory_gb instead. The hardware filter treats MPS as GPU-equivalent for the purpose of unlocking larger models, gated on ≥16 GB unified memory.

4. Candidate model pool

Ten open-source embedding models, all runnable locally on Apple Silicon (or CUDA / ROCm). Each entry carries the metadata the scorer + downstream estimators need:

  • dim — embedding dimension; drives index-size estimate
  • ctx_window — max input tokens
  • size_mb — on-disk model size
  • multilingual — true if trained for >1 language
  • requires_gpu_for_speed — true if CPU-only inference is impractical
  • embed_prefix / query_prefix — exact strings to prepend at indexing / query time ("search_document: " for nomic, "passage: " / "query: " for E5, etc.). Surfacing these is critical: forgetting them costs 5–15% retrieval quality.
  • throughput_docs_per_sec — rough CPU vs MPS rates per model, used in the embed-time estimate

The pool deliberately tops out at ~2.3 GB so the recommender remains useful on lightweight hardware. On 48 GB Apple Silicon we'd ideally extend this to include Stella-1.5B / SFR-Embedding-Mistral / NV-Embed-v2 — see the README "Roadmap" for what's planned.

After filtering, what remains is sorted by a 3-tuple score. Lower is better:

def score(model):
    window = model["ctx_window"]
    task_bonus = _task_score_adjustment(task, model)  # see §6
    if window < target_window:
        return (1, task_bonus, target_window - window)
    return (0, task_bonus, window - target_window)

# target_window = 512 if chunking_needed else max(p95_tokens, 256)

Primary key: meets the corpus's p95 token need. Secondary: task-aware preference. Tertiary: closeness to the ideal context window (penalize over-fit slightly so we don't pick an 8K-context model for a 100-token corpus when a 256-context model would do).

7. Concrete numbers (index, throughput, reranker)

Index size estimate: doc_count × dim × 4 bytes (float32, one vector per doc). Reported in MB / GB. This tells you whether you need a vector DB at all, or whether you can keep the index in memory.

Embed throughput: a per-model lookup table of CPU vs MPS rates (e.g. MiniLM ≈ 600 docs/sec on MPS, BGE-M3 ≈ 60 docs/sec on MPS). We pick the matching rate for the user's compute_device, then derive full-corpus embed time and per-query latency.

Reranker pairing: embedding-only retrieval typically saturates at ~70–75% recall@10. Adding a cross-encoder reranker (BAAI/bge-reranker-base for English, BAAI/bge-reranker-v2-m3 for multilingual) over the top-K candidates lifts that to ~85–95%. We pair one when task=retrieval, omit it explicitly with a "not applicable for this task" message otherwise.

8. LLM agent overlay (when use_llm=true)

Optional. When you tick Use local LLM agent, the LangChain create_tool_calling_agent loop runs against your local Ollama model. It calls the same tools (device_profiler, pii_remover, corpus_analyzer) and emits its own JSON. We then:

  1. Always run the deterministic baseline first (so every shape-required field is populated)
  2. Try strict JSON parse on the LLM output; if that fails, salvage with markdown-fence stripping and "first { through last }" extraction
  3. Check that the LLM's JSON has the schema-required recommended_models key (small models often dump the last tool's output verbatim — we reject that as wrong-shape and surface a debug-friendly note)
  4. Merge the LLM's judgment fields onto the deterministic baseline. Only these are overridden: recommended_models, reasoning_explanation, chunking_strategy, fine_tuning_advice, hardware_fit_analysis. The deterministic index_estimate / reranker_recommendation / language_profile always survive.

We tested this with hermes3:8b (small Ollama model), qwen3.5:9b, and qwen2.5:32b. The 8B-class models are unreliable at producing valid JSON in the right schema; qwen2.5:32b is the smallest model we found that works consistently. Set the model via SMARTEMBED_LLM_MODEL env var.

9. Privacy & security

  • Local-only by default. The recommender, the LLM (Ollama), and the embedder pool are all on-device. No API keys, no outbound calls except optional cached web search.
  • Corpus content is never logged. Only the path + character count appear in stdout. PII redactor logs the entity category (EMAIL, AADHAAR, etc.) but never the value.
  • FastAPI server binds to 127.0.0.1. Path allowlist on corpus_paths defends against arbitrary file reads if the server is ever exposed. Upload endpoint capped at 100 MB. UI uses textContent+createElement, never innerHTML, for any LLM- or user-controlled string.
  • OpenClaw skill validates user-provided paths before substituting into a shell command (single-quoted; reject shell metacharacters & >1024 chars).

See the README "Security: localhost-only by default" section for the full hardening table and instructions for safely exposing the API behind an auth proxy.

10. Known limits & honest caveats

  • The candidate pool is finite. Frontier models (Stella-1.5B, SFR-Embedding-Mistral, NV-Embed-v2, BGE-en-icl) aren't yet in the pool. On 48 GB Apple Silicon you could comfortably run a 7B-class embedder for noticeably better retrieval quality.
  • Heuristic optimizes for "fits without waste", not "best quality given the hardware budget." If you have abundant memory, the recommender currently still picks small models. A planned recommendation_priority field ("speed" / "quality" / "balanced") would address this.
  • Throughput numbers are estimates. Within ~2x of measured for typical hardware, but not benchmark-grade. Real numbers depend on batch size, sequence length distribution, and quantization.
  • MTEB scores aren't surfaced today. The pool ranks models by hardware-fit + task-fit, not by published benchmark scores. A planned MTEB-aware mode would weight quality more heavily.
  • No empirical bake-off (yet). The recommendation is a heuristic + LLM judgment, not a measured win on your data. A planned --evaluate flag would sample held-out docs, generate queries via the local LLM, and score recall@10 across the top-3 candidates.
  • Domain-specific models aren't in the pool. No CodeBERT, no PubMedBERT, no SPECTER for scientific papers, no legal-BERT. A planned domain-detection step + domain-tuned model entries would address this.
